# interface-design

設計の良し悪しは IF に出る。中の実装を読まなくても、export しているシグネチャ、その説明、依存の向きを並べれば、切り方のずれや名前の揺れは見える。この skill は、IF を並べてから当てる問いをまとめたもの。

責務をどこで分けるか（変わる理由が同じか）は `testable-design` が持つ。この skill が見るのは、分けたあとの**境界の形と名前**。両方が当たるときは、先に `testable-design` で分け方を決め、その境界にこの skill を当てる。

## 最初にやること: IF を並べる

IF を決める前、直す前、レビューする前に、対象の層が外に出しているものを全部並べる。頭の中でやらず、書き出す。

1. **export を全部並べる**: 関数、コンポーネント、hook、型。入口のファイルから出しているものと、中だけで使うものを分ける
2. **シグネチャに JSDoc を付ける**: 関数の役割、各引数、戻り値のフィールド、コールバックが呼ばれる時機。説明が書けない引数は、要る理由がまだ無い
3. **依存の向きを書く**: どれがどれを import しているかを、実際の import 文から拾う。記憶や設計の意図から描かない
4. 並べたものに、下の 1〜3 の問いを当てる

並べただけで、たいていのずれは見つかる。片方にしかない引数、同じ概念の別の名前、段の違う関数は、隣に置くと目に入る。

## 1. IF の切り方

### 包む層は、元のライブラリを外に出さない

外部ライブラリを包むモジュールを作るなら、ライブラリの型、クラス、描画の道具（canvas、DOM のノード、イベント名）を戻り値や引数に出さない。使う操作だけを持つ独自の型にする。

- なぜ: ライブラリの型を 1 つでも外に出すと、使う側がそのメソッドを直接呼び始め、包んだ意味がなくなる。版上げのときに直す場所が、包む層の外に広がる
- 自分に問う: 「この IF はライブラリのものをそのまま持ってきているか、抽象化しているか」。半分だけ抽象化している状態がいちばん読みにくい
- ライブラリと同じ形をあえて残す型があってよい。そのときは「わざと同じにしている」と説明できること

### 並ぶ関数の抽象度をそろえる

同じモジュールが出す関数は、同じ段の言葉で書く。「もの」を返して寿命を持つ関数と、道具を受け取って 1 回処理するだけの関数を並べない。

- 始めと終わりを対にする: 開く / 閉じる、置く / 外す、購読する / 解除する。対になる終わりが無い関数は、段が低いか、寿命の持ち主が決まっていない
- 出すものを種類で分け、種類の中では形をそろえる。たとえば「資源（開いて閉じる）」と「表示（置いて外す）」の 2 種類にして、表示の関数はどれも「資源と置き場所を受け取り、外す手段を返す」形にする
- なぜ: 段がそろっていないと、使う側が関数ごとに違う作法を覚えることになる。片方だけ低い段だと、その分の道具と手順が使う側に漏れる

### 兄弟の IF を突き合わせる

似た役割の関数やコンポーネントを隣に置き、引数を 1 つずつ比べる。

- 片方にしかない引数は、要る理由を問う。「こちらには無いのに、なぜこちらには要るのか」。答えが「実装の都合」なら、たいてい同じことを 2 か所で言っている（CSS で決めた大きさを引数でもう一度渡す、など）。片方から導けるなら引数を消す
- コールバックの必須 / 任意も兄弟でそろえる。使い手が 1 つしか無いコールバックが必須になっていないか

### 上の層を組み直したら、下の層も見直す

使う側の整理が進むと、下の層の切り方が古い形のまま残る。上を「開く」と「2 通りに見せる」に整理したのに、下は「先に器を作って後から中身を入れる」のまま、というずれが起きる。上の層を直したら、その下の IF をもう一度並べて、同じ考え方で切れているかを見る。

### 特殊な形より一般の形

「最初の 1 件」「既定の 1 つ」に限った名前と作りにしない。番号や識別子を受け取る一般の形にして、使う側が `1` を渡す。

- なぜ: 特殊な形は、2 つ目の使い道が出たときに名前ごと作り直しになる。一般の形でも実装の手間はほぼ変わらない
- ただし、要望の無い柔軟さは足さない。一般化するのは、名前と引数が特殊な値に縛られているときだけ

### コンポーネントを分けるのは、意味のある差分があるときだけ

似たコンポーネントが複数あるなら、「分ける合理的な理由があるか。使う場所ごとに意味のある差分があるか」を問う。

- 差が「この部分が要る / 要らない」だけなら、コンポーネントを分けずに props で出し分ける
- `testable-design` の「共通部にフラグが増え続けていないか」とは向きが違う。あちらは、変わる理由の違うものを 1 つにまとめた結果のフラグを指す。同じものの一部を出す / 隠すだけの props は、それに当たらない。迷ったら「片方の画面の要望で直したとき、もう片方の振る舞いが変わるか」で決める

### ある使い手の都合を、下の層の IF に出さない

1 つの画面の見た目の都合（縦横で切り取り方を変える、など）のために、下の層のコールバックに値を足さない。CSS やレイアウトだけで同じ結果になるなら、そちらに寄せる。IF が 1 つ減り、途中の層を素通しする props も消える。

### 状態の持ち主は 1 か所

- 同じ値を、引数と setter の両方から変えられる形にしない。持ち主を 1 つに決め、ほかは受け取るだけにする
- 同時に起きない状態（読み込み中、入力待ち、失敗、完了）は、複数の真偽値や nullable の組ではなく、1 つの判別可能な値で持つ

### 依存は一方向、入口は 1 つ、lint で縛る

- 層の向きを決めたら（例: 画面 → 共通のコンポーネント → 包む層 → ライブラリ）、その向きを lint の import 制限で縛る。口約束にしない
- 外から読めるのは入口のファイルだけにする。中のファイルを相対パスで読む道も塞ぐ
- CSS のような副次の import も例外にしない。値として再 export できないものは、包む層の中で読み込む
- lint を足したら、各層に仮のファイルを置いて、止まるべき import が止まり、通るべき import が通ることを確かめる。override がルールの設定を丸ごと差し替える linter では、既存の制限が消えていないかも見る

## 2. props と export を残すか外すか

1 つずつ、次の問いに答える。答えられないものは外す。

| 問い | 外す・直す目安 |
|---|---|
| 何のために必要か | 理由が「念のため」「将来使うかも」 |
| どこで使うか | 使い手が 0。または 1 つだけなのに、共通の IF を何段も素通ししている |
| export は必要か | 中でしか使っていない。テストのためだけに出している |
| 上限、下限、範囲外の値でどう動くか | 説明に書いていない。聞かれてから調べることになる |

### props の書き方

- **真偽の props に `is` を付けない**。プロジェクトのデザインシステムや UI ライブラリの書き方に合わせる（`disabled`、`loading`、`downloadable`）。ローカル変数や state の `isXxx` は別の話で、ここでは props の名前だけを指す。プロジェクトに別の規約があればそちらに従う
- **`className` / `style` を props に出さない**。できることが多すぎて、コンポーネントのどの要素に当たるかを使う側が予想できない。要るのが「幅いっぱいに出す」「切り取る」のような決まった見た目なら、置き場所の要素を使う側に持たせるか、意味のある props にする
- **値の名前は、実際に区別していることを言う**。失敗の理由が `"failed"` では何も言っていない。区別していないなら `"unknown"` とし、何をまとめているかをコメントに書く

### 見た目だけのコンポーネントを分けたら

状態を持つコンポーネント、見た目だけのコンポーネント、ライブラリにつなぐコンポーネントに分けたら、それぞれの役割を表にする。見た目だけのコンポーネントについては、渡すハンドラと値を**どこで作るか**（どのコンポーネントが状態の持ち主か）まで書く。分けただけで持ち主が書かれていないと、読む人は結局中を追うことになる。

## 3. 命名の一貫性

名前は 1 つずつ決めず、全部を並べてから決める。

- **名前にライブラリの名前を出さない**。包む層の外にある関数、hook、コンポーネント、ファイル名に、ライブラリ名やその略を入れない。入れてよいのは、包む層そのものの置き場所の名前まで
- **同じ概念は、層をまたいでも同じ語**。包む層とコンポーネントで `pageNumber` と `currentPage`、`pageCount` と `numPages` のように揺らさない。引数名（`value` か `scale` か）まで含めてそろえる
- **似ているが違う概念は、呼び分ける**。指定した値と実際に当たった値のように、取り違えると不具合になるものは、別の語を決めて両方の層で使う
- **コールバックの形をそろえる**。`onXxxChange` と `onSetXxx`、`onGoToXxx` を混ぜない
- **対になるコンポーネントは、同じ付け方をする**。入口から出すコンポーネントと中のコンポーネントの関係を、接尾辞の付け方で一貫させる
- **用途の系列でそろえる**。同じ用途の関数、コンポーネント、一覧は、同じ語幹を持つ名前にする
- **先に言葉の表を作る**。使う語（もの、集まり、1 つ、見せるコンポーネント、完成品など）と意味を表にし、名前はそこから組み立てる。表に無い語を使いたくなったら、表を直すのが先
- **好みが分かれる名前は、決めずに聞く**。機械的にそろえられるもの（揺れの統一）は進め、どちらもあり得る命名の方針は候補を並べて選んでもらう

名前を変えたら、コード、テスト、ドキュメント、図、設計書の全部を同じ名前にする。

## 4. 見せ方と進め方

### 設計は IF で見せる

設計を説明するときは、文章での要約より先に「最初にやること」で並べたもの（シグネチャ、JSDoc、依存の向き）を見せる。読む人は IF から設計を判断する。型は記憶から書かず、実際のコードから写す。

### 図は実体と 1 本ずつ突き合わせる

- 図に描く名前は、今の実装に実在するものだけ。設計案の名前と実装の名前を混ぜない。混ぜるなら、どちらの時点の図かを書く
- 矢印は、実際の import と呼び出しを 1 本ずつ確かめてから引く。「中のコンポーネントが呼んでいる」を「外のコンポーネントが呼んでいる」と描かない
- import の線と、受け取った値のメソッドを呼ぶだけの線は、線の種類で分ける
- 図から省いたものがあれば、何を省いたかを添える
- コードを変えたら、図も同じ手順で確かめ直す。図だけが古い状態は、無い図より悪い

### 画面とコンポーネントの対応を示す

コンポーネントの切り方を説明するときは、実際の画面のスクリーンショットにコンポーネントの境界を重ね、どの部分がどのコンポーネントかを示す。入れ子の図を添えると、使う場所ごとの違いが「外側に何を足しているか」として見える。

### 大きな組み直しは、設計書が先

IF の組み直しや名前の付け替えが複数の層に及ぶなら、実装より先に設計書（IF、言葉の表、図）を直し、合意してから実装する。途中で方針が変わっても、直すのは設計書だけで済む。

### 設計書に経緯を書かない

設計書に残すのは、変更前と変更後の差分と、今の形の理由。試して捨てた案の経緯は、読む人の判断に要らない。見送った案を残すなら、最後に表でまとめる。確かめていないことは、確かめていないと書く。

## レビューするとき

自分の差分でも他人の PR でも、「最初にやること」で IF を並べてから、次の順で当てる。

1. 包む層の外に、ライブラリの型、道具、名前が漏れていないか
2. 並ぶ関数の段がそろっているか。始めと終わりが対になっているか
3. 兄弟の IF に、片方にしかない引数や、必須 / 任意の不ぞろいがないか
4. 使い道を答えられない props、コールバック、export がないか
5. `className`、`is` 付きの真偽 props、何も言っていない値の名前がないか
6. 同じ概念に 2 つの名前がないか。コールバックの形が混ざっていないか
7. 依存の向きが lint で縛られているか。入口以外を外から読んでいないか
8. 図とドキュメントの名前と線が、実装と合っているか

指摘には、どの IF のどの引数や名前かと、そのままだと使う側で何が起きるかを添える。「一貫性がない」だけの指摘はせず、揺れている名前を並べて示す。
