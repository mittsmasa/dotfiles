# 実行基盤と AI エージェント

Dockerfile、コンテナ、ランタイムの更新、AI エージェントの設定と組み込みを扱うときに読む。

## 実行基盤

### サポート版を使い、更新を稼働環境まで届ける

- OS、言語ランタイム、ベースイメージはサポート期間内のものを使う。EOL のものは、動いていても新しい脆弱性が直らない
- 更新は、稼働中の環境に反映されて完了とする。kernel は再起動、コンテナは再ビルドと置き換え、マネージドサービスはメンテナンスの適用が別に要ることがある
- 確かめ方: 稼働中のコンテナやノードで実際のバージョンを見る（`node --version`、`uname -r`、イメージの digest）

### 使っていない機能を止める

- 使っていないパッケージ、ポート、デバッグ機能、ネットワーク機能を無効にする。脆弱性があっても、使えなければ攻撃が成り立ちにくい
- Dockerfile では multi-stage build で実行イメージからビルドツールを外し、distroless や slim のイメージを選ぶ
- 止めるとサービスが壊れることがあるので、依存関係を見てから止める

### 信頼できないワークロードをホストから離す

- コンテナは非 root ユーザーで動かす（`USER`、`runAsNonRoot`）
- `privileged`、host namespace（`hostNetwork`、`hostPID`）、`hostPath`、Docker socket のマウントは、本当に要るときだけ使う。どれもホストへの強い権限になる
- 複数のワークロードや利用者が同じ基盤を共有する CI runner では、ジョブごとに使い捨ての環境にする

## AI エージェントを使うとき（推奨）

この節の項目は推奨であり、未導入だけを理由に作業を止めない。扱う情報と操作の影響に応じて、効く対策から足す。

### 3 つの条件を同じ実行でそろえない

エージェントは、読み取った文章の中の指示と、人間からの正当な指示を確実には区別できない。次の 3 つが一つの実行でそろうと、第三者がエージェントを誘導して情報を持ち出せる（プロンプトインジェクション）。

- (A) 第三者が中身を操作できる情報を読む（Web ページ、Issue、PR、メール、ツール出力、依存のドキュメント）
- (B) 秘匿情報、機密データ、本番環境に届く
- (C) 外部へ送る、または状態を変える（書き込み、commit、API 呼び出し、メッセージ送信）

3 つがそろう作業を一律に禁止はしない。通常のコード編集、build、test、作業ブランチへの push は自動で進めてよい。機密情報を外へ送れる、本番を変えられる構成のときに、権限、通信先、実行環境のどれかを絞る。

不可視文字や HTML コメントを取り除く前処理は補助にはなるが、それだけでは防げない。権限の分離と組み合わせる。

### 権限を作業に必要な分だけにする

- エージェントを本人と同じ権限で動かさない。本番管理用の認証情報や、作業に要らないクラウドの権限を実行環境に持ち込まない
- MCP サーバの読み書き権限と、取れるデータの範囲を確かめる。読み取り専用でも、すべての機密データを読んでよいとは限らない
- 外部 PR を処理する CI のエージェントには、デプロイ用、公開用の認証情報を渡さない
- リリースなど権限が大きく変わる作業は、通常の開発エージェントとは別の権限と手順で行う

### 不可逆・高影響な操作は単独で完結させない

- 本番デプロイ、パッケージ公開、保護ブランチへの反映、大量削除、権限変更、外部へのメッセージ送信は、人間の承認か、エージェントの判断によらない仕組み（branch protection、environment の承認）の下に置く
- エージェントの permission 設定やプロンプトを、本番操作を止める唯一の手段にしない。利用者が書き換えられる設定は防壁として弱い
- すべての tool に承認を求めると、承認が形だけになる。通常の作業は自動で進め、実害の大きい操作だけを止める
- AI が作った変更にも通常のレビューとテストを当てる。別の AI のレビューは、独立した承認の代わりにならない

### 実行環境を隔離する

- 普段の端末で直接動かすと、作業対象外のファイル、認証情報、ローカルネットワークに届く。クライアントの sandbox、devcontainer、VM、クラウドの sandbox を使う
- 無人実行や外部 PR の処理は、より強い隔離（使い捨ての VM や runner）で動かす
- Web 検索、Git 操作、依存の取得は通常の開発に要る。一律に止めず、ホストの認証情報と本番への到達を絞る

### 挙動を決める設定をレビュー対象にする

次のファイルはエージェントの動きを変える。第三者が書き換えると、意図しない操作をさせられる。

- 指示ファイル（CLAUDE.md、AGENTS.md、ルールファイル）
- MCP サーバの設定と、各 tool の説明文
- hook、カスタムコマンド、skill、plugin
- permission 設定、許可リスト、拒否リスト

扱い方:

- 共有する設定は Git で管理し、コードと同じくレビューする。エージェントが作業ブランチで編集するのは構わない
- 外のリポジトリから取り込んだ指示ファイル、MCP 設定、hook、skill は、有効にする前に中身を読む
- MCP サーバや plugin は第三者のコードなので、`supply-chain.md` の観点も当てる
- 不可視文字など diff で気づきにくい変更は、必要なら CI で検査する

### 行為を追えるようにする

- エージェントの作業の責任は、任せた人か運用するチームにある
- まずハーネスのセッション履歴、Git の履歴、PR、CI の結果、操作先サービスの監査ログで追えるかを見る。追えるなら、同じ情報を残す仕組みを足さない
- 無人実行などで既存の記録だけでは追えないときに限り、run ID や session ID など足りない情報だけを残す

## 製品に AI エージェントを組み込むとき（推奨）

利用者の代わりに DB や SaaS を操作する機能では、モデルが誤った対象や利用者 ID を指定しても、他人のデータに届かないようにする。

- 認可は tool と backend で、要求元の利用者に対して強制する。RAG の検索結果や MCP 経由のデータにも同じ認可を当てる。共有アカウントで接続する場合も、利用者本人より広い範囲のデータをモデルに渡さない
- モデルの出力は信頼できない入力として扱う
  - tool の引数をスキーマと業務ルールで検証する
  - モデルが作った SQL、コマンド、URL を実行するなら、実行範囲を絞り、隔離する
  - HTML に表示するなら無害化する（XSS 対策）
  - backend で URL を取得するなら、内部アドレスへの接続を止める（SSRF 対策）
- 決済、予約の取消など本人の意思確認が要る操作は、対象と内容を見せて確認を取る
- 大量の呼び出しでサービスが止まらないよう、レート制限と上限を置く
- テストでは「別の利用者の ID を引数に入れた tool 呼び出しが拒否される」ことを確かめる
