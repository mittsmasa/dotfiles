# コードを届ける経路と、認証情報

CI/CD workflow、署名、公開・デプロイ、認証情報と環境変数を扱うときに読む。例は GitHub Actions で書くが、考え方は他の CI でも同じ。

## 外部からの PR と秘匿情報を分ける

外部からの PR に含まれる変更は、レビュー前は「第三者が書いた信頼できないコード」として扱う。その PR で CI を動かすのはよいが、秘匿情報と書き込み権限は渡さない。

- `pull_request_target` は必要なときだけ使う。使うなら PR のコードを checkout して実行しない。このトリガーは base ブランチの権限と secrets で動くため、PR のコードを動かすとそれらが渡る
- `workflow_run` で、未信頼なジョブが作った artifact を受け取るときも同じ。artifact の中身を実行しない
- cache と artifact は前のジョブのファイルを次に渡す。未信頼なジョブが作ったものを、秘匿情報を持つジョブで復元しない
- PR タイトルや本文など、外部が書ける値を `run:` に `${{ }}` で直接埋めない。いったん `env:` に入れてシェル変数として参照する（script injection 対策）
- `GITHUB_TOKEN` の既定権限は読み取りにし、`permissions:` でジョブごとに必要な分だけ足す

## 変更者を確かめられるようにする

Git の author 名とメールアドレスは誰でも自由に書ける。それだけで変更者を判断しない。

- ホスティングの認証（保護ブランチ、必須レビュー）や commit 署名で確かめる
- 署名鍵は端末が乗っ取られても使われないように守る。ハードウェアやセキュアエンクレーブに鍵を置く、パスフレーズや生体認証を挟むなど

## 公開と本番更新を独立した承認の下に置く

パッケージの公開と本番の更新は、一度走ると利用者全体に届く。CI や開発端末のどれか一つが乗っ取られても、そこから公開や本番更新まで完結できないようにする。

- GitHub の environment に required reviewers を設定し、公開・デプロイのジョブをその environment で動かす
- 公開用、デプロイ用の認証情報は、その environment にだけ置く
- 手で公開する運用なら、公開権限を持つ人と変更を作る人を分ける

## 長寿命の静的な認証情報を避ける

アクセスキーや API トークンは、漏れると失効するまで使われ続ける。複数の用途で共有すると、漏れたときの被害も広がる。

- CI からクラウドやレジストリに入るときは OIDC を使い、実行主体に紐付いた短寿命のトークンに交換する。GitHub Actions ではジョブに `permissions: id-token: write` を付け、クラウド側の信頼条件をリポジトリ、ブランチ、environment で絞る（`id-token: write` の書き方は各クラウドの公式手順で確かめる）
- npm などの公開も、対応していれば trusted publishing（OIDC）を使う
- 短寿命にできないトークンは用途ごとに分け、権限、対象、期限を絞る。使わなくなったら失効させる

## 秘匿情報が届く範囲を絞る

秘匿情報は、安全な場所にしまうだけでは足りない。乗っ取られた端末やジョブからその場所に届けば、攻撃者も取り出せる。

- 依存のインストール、lint、test、build のジョブやステップには、秘匿情報を渡さない。`env:` はジョブ全体でなく、使うステップにだけ書く
- 開発端末でも、シェル全体に export せず、必要なコマンドにだけ渡す（`op run --`、`fnox exec --`、`aws-vault exec` などのラッパー）
- 秘匿情報をコード、ログ、コミット、PR 本文、URL のクエリに書かない。CI のログでマスクされない加工（base64 など）もしない
