# 責務分離

コードを書く前と、書かれたコードをレビューするときに当てる責務分離の観点の詳細。出典は `sources.md` の後半にある。テストコードの観点は `test-quality.md` が持つ。

## 判定の軸

軸は 1 つだけ: **変わる理由が同じものは一か所に集め、違うものは離す**（Martin）。

- 変わる理由は「人」で数える。仕様の変更を頼んでくる人（または、まとまって動く 1 つのグループ）が 1 つなら、責務は 1 つ
- バグ修正とリファクタは変わる理由に数えない
- 責務分離が崩れた状態は 2 方向にある
  - **混ざりすぎ**: 1 か所に複数の人の要望が同居している。片方の要望で直すと、もう片方が壊れる
  - **散らばりすぎ**: 1 つの要望の変更が複数箇所に波及する。直し漏れがバグになる
- 分けたことで得たいのは、変更時に読む範囲が狭まることと、片方を直してももう片方が壊れないこと（Fowler）。ファイル数や抽象の多さは目的にしない
- 行数・ファイル数・関数の長さでは判定しない。300 行でも変わる理由が 1 つならよく、20 行でも 3 つ混ざっていれば崩れている

## 分ける前に当てる問い

境界を決める前と、既存コードに足す前に、次の 3 つを自分に問う。

1. このコードの変更を頼んでくるのは誰か。2 人以上いるなら、どこで分かれるか
2. 「〜を変えたい」という要望を 1 つ想定したとき、直すのは何か所か。1 か所に収まるか
3. いま足そうとしているものは、隣にあるものと同じ理由で変わるか。同じでないなら、同じ場所に置かない

答えられないなら、要件がまだ見えていない。推測で分割や共通化を進めず、まとまった形のまま書いて、変わる理由が見えてから分ける。

## 観点

1 と 2 が軸そのもので、3〜7 は軸の崩れを見つけるための症状。8 は逆方向の失敗。

### 1. 変更を頼む人が一人に絞れるか

- 崩れているサイン: 1 つの関数・コンポーネントに、入力の検証（プロダクトが決める）、計算ルール（業務部門が決める）、保存方法（開発が決める）、通知文面（運用が決める）が並んでいる
- 直し方: 人ごとに関数・モジュールを分け、元の場所はそれを順に呼ぶだけにする。順に呼ぶこと（オーケストレーション）も 1 つの責務として残してよい

### 2. 1 つの要望の変更が何か所に散らばるか

- 崩れているサイン: 同じ業務ルール（合格点 60 点、締切は前日 23:59 など）の条件式やリテラルが、表示・判定・出力など複数の場所に直接書かれている
- 外部サービスの知識（ベース URL、認証方式、エンドポイント）も同じ。複数ファイルに書かれていると、認証の方式が変わったときに全部を直すことになる。同じ環境変数の読み取りが散っていれば、その兆候
- 直し方: ルールを名前の付いた関数か定数 1 か所に置き、全員がそれを参照する

### 3. 共通化したものは、本当に同じ理由で変わるか

エージェントが最も起こしやすい崩れ。見た目やコードが似ているだけで 1 つにまとめる。

- 崩れているサイン:
  - 共通コンポーネント・関数にフラグ引数、`variant`、`mode`、`isXxx` が増え続けている
  - 呼び出し元ごとの分岐が共通部の中にある
  - 片方の画面の要望で共通部を直すと、もう片方に影響する
- 直し方: 変わる理由が違うなら、似ていても重複を許して別々に持つ。共通化するのは、同じ業務知識（同じルール、同じ定義）を表しているときに限る。見た目が同じコードの重複は、同じ知識の重複とは限らない

### 4. 知らなくていいことを知っていないか

- 崩れているサイン:
  - UI が API レスポンスや DB の行の形を奥まで辿っている（`data.a.b.edges[0].node.c.id`）
  - 業務ロジックが HTTP ステータス、GraphQL のエラー型、フレームワークのリクエストオブジェクトを受け取る・返す
  - API の入口（resolver、controller、route handler）の中に業務ルールの条件分岐が並んでいる
  - 表示用のテンプレートに SQL やデータ取得が書かれている
- 直し方: 境界で形を変換する処理を 1 か所に置き、内側には内側の言葉（`courseId` などの業務上の値）だけを渡す。外側の形が変わっても、直すのは変換処理だけで済むようにする

### 5. テストするのに関係ない準備が要らないか

- 崩れているサイン: 1 つの判定ロジック（締切を過ぎたか、割引が適用されるか）を確かめるのに、DB、API クライアント、現在時刻をまとめてモックしないといけない
- 直し方: 判定を、必要な値を引数で受け取る純粋な関数に切り出す（`isOverdue(deadline, now)`）。データ取得や現在時刻の取得は呼び出し側に残す

### 6. 一文で、接続詞なしに説明できるか

- 崩れているサイン:
  - 名前が何でも入る形になっている（`handleData`、`processUser`、`manager`、`utils`、`helpers`、`common`）
  - 役割を説明すると「〜して、〜して、それから〜する」と続く
- 直し方: 「〜を〜する」の一文で言える単位まで分ける。名前が付けられないなら、責務がまだ決まっていない。名前に「and」や「や」が要るなら 2 つに分ける

### 7. 変更のために読む範囲は狭いか

- 崩れているサイン: 文言 1 つ、条件 1 つを変えたいだけなのに、データ取得・権限判定・状態管理が絡んだ長い本体を全部読まないと安全に触れない
- 直し方: よく変わる部分（表示、文言、閾値）と、変わりにくい部分（データ取得、権限）を分け、変える人が読む範囲を前者だけにする

### 8. 分けすぎていないか

分けすぎも「同じ理由で変わるものが離れている」状態で、観点 2 と同じ失敗。

- 崩れているサイン:
  - 呼び出し元が 1 つしかないのに、`interface` / `Impl` / `Factory` / `Mapper` / `Adapter` に分かれている
  - 1 つの変更のたびに 4 ファイル以上を行き来する
  - 差し替える予定のない層を「将来のため」に挟んでいる
  - 中身が 1 行の委譲だけの関数・ファイルが連なっている
- 直し方: 同じ理由で変わるものは同じ場所に戻す。抽象は、差し替えやテストの必要が実際に出てから足す

## 書くときの手順

アプリケーションコードを書く・直す前に、この順で当てる。

1. 変更要望を 1 文で書き、それを頼んだ人を特定する
2. その要望で直す既存の場所を探す。同じルールがすでにどこかにあるなら、そこを直す（新しく書き足さない）
3. 足すコードが、置こうとしている場所の既存コードと同じ理由で変わるかを確かめる。違うなら、置き場所を変える
4. 既存の共通部に手を入れる必要が出たら、まず観点 3 を当てる。フラグや分岐を 1 つ足す前に、呼び出し元を分けるほうが自然でないかを比べる
5. 新しい分割や抽象を足すなら、それを必要とする変わる理由を 1 文で言えることを確かめる。言えないなら足さない
6. 書き終えたら、別の人の要望（文言変更、ルール変更、保存先変更など）を 1 つ想定し、何か所を直すことになるかを数える

既存コードの責務が崩れていても、依頼の範囲外なら直さない。見つけた崩れは、報告に一文で書くか、別タスクとして提案する。

## レビューの出し方

書かれたコード（diff / PR）をレビューするときは、次の順で当てる。

1. 変更ごとに、変わる理由（誰の要望か）を特定する。1 つの関数・コンポーネントに 2 つ以上の理由が入っていないか（観点 1）
2. 今回の要望の変更が、複数の場所に同じ形で入っていないか（観点 2）
3. 共通部にフラグ・分岐・`variant` が増えていないか（観点 3）
4. 層をまたいで外側の形が内側に漏れていないか（観点 4）
5. 分けすぎていないか（観点 8）
6. 名前・読む範囲・テストのしやすさ（観点 5〜7）

指摘には、当たる観点の番号と、壊れる具体シナリオを添える。シナリオは「どの人のどの変更要望で、どこが一緒に壊れるか（または何か所直すことになるか）」の形で書く。

- 例: 「観点 3: 管理画面だけ email を出したい要望で `UserCard` に `showEmail` を足すと、生徒画面のスナップショットと表示条件も一緒に変わります。管理画面用のカードを別に持つのはどうでしょうか」

観点名だけの指摘、行数やファイル数だけを根拠にした指摘はしない。崩れていても今回の変更が新たに悪化させていないなら、既存の問題として分けて書く。
