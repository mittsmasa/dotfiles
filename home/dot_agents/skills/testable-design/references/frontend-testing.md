# フロントエンドのテスト戦略

React フロントエンドで、観点ごとにテストレイヤーを選び、テストしやすい形に実装を分けるための指針。

- テストの書き方（振る舞いを確かめる、書かない判断、クエリの優先順位など）は `test-quality.md` に従う
- 責務分離の判定（変わる理由で分ける）は `separation-of-concerns.md` に従う

## 原則

**ひとつの観点は、それを検証できる一番安いレイヤーで、一度だけ検証する。**

テストのしやすさは実装の分け方で決まる。安いレイヤーで検証できないなら、テストを複雑にする前に実装の分割を見直す。

## テストを書く前の手順

1. **観点を列挙する**: 今回の変更で守りたい振る舞いを箇条書きにする
2. **実装の層を確認する**: 対象コードが「実装の層分け」に沿っているか見る。ロジックや副作用がコンポーネントに埋まっていて安いレイヤーで検証できないなら、切り出しを計画に含める
3. **レイヤーを割り当てる**: 「観点 → レイヤー対応表」で、各観点をちょうど一つのレイヤーに割り当てる
4. **計画を示す**: 「観点 → レイヤー → テストファイル」の一覧と、必要なら切り出し案をユーザーに示してから書き始める
5. **重複を確かめる**: 既存のテストや Story が同じ観点を検証していないか探す。あれば足さずに既存を更新する

## 観点 → レイヤー対応表

| 観点 | レイヤー |
|---|---|
| 計算・変換・バリデーション・日付や金額・状態遷移（reducer）・権限判定などの純粋なロジック、境界値の網羅 | 単体テスト（Vitest） |
| カスタムフックのロジック・副作用の制御 | 単体テスト（`renderHook`）。UI と一体でないと意味がないものはコンポーネントテスト |
| 操作に応じた表示の変化、条件付き表示、フォームのエラー表示、disabled、フォーカス移動、role とラベルで引けること（a11y）、レイアウトや実ブラウザ API（IntersectionObserver、ResizeObserver、スクロール）に依存する振る舞い | コンポーネントテスト（Vitest Browser Mode） |
| 画面と API のやり取り: 送るリクエストの中身、ローディング / エラー / 空状態の出し分け、500・タイムアウト・ページング境界、キャッシュ無効化 | MSW を使った結合テスト / E2E |
| 重要なユーザー導線が端から端までつながっていること | 実バックエンド E2E（Playwright） |
| 見た目（余白・色・レイアウト・ダークモード・デザイントークン変更の影響） | VRT（撮影対象の Story が前提） |
| コンポーネントの状態のバリエーション | Storybook の Story（VRT とテストの入力データ） |
| 型・API スキーマとの整合 | 静的検査（TypeScript / スキーマから生成した型） |

迷ったら「この観点を検証できる一番安く速いレイヤーはどれか」で決める。

この表は汎用の既定値。プロジェクトに規約があれば、レイヤーの割り当てはそちらに従う（SKILL.md の「プロジェクトの規約との関係」）。たとえば、操作の検証を Story の `play` に寄せる、データ取得の状態を Story の MSW で作る、実バックエンド E2E を持たない、というプロジェクトでは、該当する行をその規約の層に読み替えるか、外して考える。外した行の観点（送るリクエストの中身、キャッシュ無効化など）がどの層でも確かめられていないなら、そのことを報告に書く。

## レイヤーごとのルール

### コンポーネントテスト（Vitest Browser Mode）

- 既定の実行環境は Vitest Browser Mode（実ブラウザ）。jsdom は既存プロジェクトがすでに jsdom で揃っていて、まだ移行していない場合に限る。新しく書くテストは Browser Mode で書く
- 描画は `vitest-browser-react` の `render`、要素の取得は `page` のロケーター（`getByRole` など。優先順位は Testing Library と同じ）を使う
- 操作は `vitest/browser` の `userEvent` を使う。`fireEvent` 相当の合成イベントは使わない
- アサーションは `expect.element(locator)` を使う。要素が現れるまで待つので、`waitFor` や固定時間の sleep を書かない。要素が無いことは `expect.element(locator).not.toBeInTheDocument()` で確かめる
- jsdom のまま残っているテストでは、非同期は `findBy*` で待ち、要素が無いことは `queryBy*` で確かめる。`waitFor` の中にはアサーションを 1 つだけ入れ、操作や副作用を書かない。`userEvent.setup()` はテストごとに呼ぶ
- a11y は role とラベルで引けることに加えて、axe による自動検査（Storybook の a11y アドオンなど）で違反を拾う
- Error Boundary、Portal、Suspense、Context は本物を使って描画する。Provider はテスト用の `wrapper` にまとめ、各テストで組み立てない。Error Boundary のテストで出る想定内の `console.error` は、そのテストの中だけで抑える
- 純粋関数や、DOM を使わないフックのロジックは Browser Mode に載せず、Node 環境の単体テストで確かめる。ブラウザを立ち上げる分だけ遅くなるため

### MSW を使った結合テスト / E2E

- 正常系に加えて、エラー・空・遅延のハンドラを用意し、出し分けを確かめる
- 送ったリクエストを確かめたいときは、ハンドラ内で受け取ったリクエストを記録して検証する
- ハンドラと fixture は Story と共通化する（「テスト資産の共通化」）

### 実バックエンド E2E（Playwright）

- 対象は重要な導線だけ（例: ログイン → 主要業務の完了）。目的は「つながっていること」の証明
- 分岐やエラーケースは網羅しない。それは MSW 層の仕事
- 新しい導線の E2E を足すときは、MSW 層では足りない理由を計画に書く
- 何度流しても同じ結果になるようにする: テストごとに一意な ID でデータを作り、終わったら後始末する。並列実行で他のテストのデータとぶつからないようにする

### Storybook

- Story は VRT の撮影対象であり、テストの入力データ（状態のカタログ）でもある
- 表示コンポーネントの Story は props だけで書く。データ取得を含む画面単位の Story が必要なときだけ MSW を使う
- `play` 関数のインタラクションテストはコンポーネントテストと役割が重なる。プロジェクトでどちらに寄せるか決まっていればそれに従い、両方には書かない。決まっていなければ近くの既存コードに合わせ、どちらで書くかを計画に明記する

### VRT

- VRT の対象はデザインシステムと重要画面に絞る（動的コンテンツは flaky になりやすい）
- VRT は Story を撮影対象にする。対象にしたいコンポーネントに Story がなければ、まず Story を作る
- 見た目に影響する変更をしたら、対応する Story を追加・更新する
- 見た目の回帰は VRT に任せ、色・余白・クラス名をアサーションで確かめない
- 撮影対象の Story は、状態のバリエーション（空・エラー・長い文字列・ダークモード）を網羅する

## 実装の層分け

コードを次の層に分け、層ごとに担当するテストレイヤーを固定する。下の層ほど React と副作用から遠く、安くテストできる。

| 層 | 中身 | 依存してよいもの | 担当するテスト |
|---|---|---|---|
| ドメインロジック | 計算・判定・変換・バリデーションスキーマ・状態遷移（reducer）。すべて純粋関数 | なし（React も非同期処理も持たない） | 単体テスト |
| API クライアント | リクエストの組み立て、fetch、レスポンスのパース（スキーマ検証） | fetch、型 / スキーマ | MSW 層でまとめて確かめる。変換が複雑なら純粋関数に出して単体テスト |
| データ取得フック | API クライアントを呼ぶ。キャッシュキー、再取得、ミューテーション後の無効化 | API クライアント、データ取得ライブラリ | MSW を使った結合テスト |
| 振る舞いフック | 画面の状態、イベントハンドラ、副作用（購読・タイマー・ストレージ・ブラウザ API）をまとめる | ドメインロジック、データ取得フック | 単体テスト（`renderHook`）またはコンポーネントテスト |
| 表示コンポーネント | props を受けて描画し、イベントをコールバックで返すだけ | props、他の表示コンポーネント | Story + VRT。操作による表示変化はコンポーネントテスト |
| つなぎ込み（コンテナ / ページ） | フックと表示コンポーネントをつなぐだけ。ロジックを持たない | 上記すべて、ルーター | MSW を使った結合テスト。重要導線は実バックエンド E2E |

### 切り出しのルール

- **ロジックは純粋関数に出す**: 判断基準は「このロジックを確かめるのに render が要るか」。要らないのに render しないと確かめられないなら切り出す
- **API 呼び出しは API クライアントに集める**: コンポーネントやフックから直接 fetch しない。通信が一か所を通るので MSW で一律に差し替えられ、`vi.mock` が要らなくなる
- **レスポンスから画面用データへの変換は純粋関数で行う**: セレクタやマッパーとして切り出し、単体テストで網羅する
- **副作用はカスタムフックに閉じ込める**: コンポーネント本体に `useEffect` を散らさない。一つのフックは一つの副作用の関心事に絞る
- **`useEffect` で派生状態を作らない**: props や state から計算できる値はレンダー中に純粋関数で計算する。イベントで起きる処理はイベントハンドラに書く
- **非決定的な依存は外から渡す**: 現在時刻、乱数、ID 生成、localStorage、`window` は引数か注入で受け取る。テストではグローバルの差し替え（`vi.setSystemTime`、`vi.stubGlobal`）より、引数で渡せる設計を優先する
- **表示コンポーネントは外の世界に直接依存しない**: データ取得、グローバル状態、ルーターを直接使わず props で受ける。Story が props だけで書けるので、VRT にもそのまま乗る
- **つなぎ込み層は薄く保つ**: ページやコンテナに分岐や計算が増えたら、フックか純粋関数へ移す
- **Server Component / Server Action も薄く保つ**: ロジックは純粋関数に出して単体テストする。Server Component 自体の描画は結合テストや E2E に任せ、単体で render しようとしない
- **モックが 3 つ以上要るなら分け方を疑う**: テストを書き進める前に、上の層分けに沿っているかを見直す

## 後片付けと分離（実行順に依存しないために）

片付けは手で書かず設定で自動にし、そもそもテスト間で共有する状態を持たない。

### モック

- `vi.spyOn` の差し替えは `restoreMocks: true` で各テスト前に自動で戻す。公式に対象と明記されているのは `vi.spyOn` だけなので、`vi.fn` の呼び出し履歴は `clearMocks` か `mockReset` で消す。非同期テストを並行実行していると、一つのテストの復元が実行中の別テストの spy まで戻すので、並行実行と組み合わせない
- `vi.stubGlobal` / `vi.stubEnv` は `unstubGlobals: true` / `unstubEnvs: true` で自動的に戻す
- fake timers を使ったら `afterEach` で `vi.useRealTimers()` に戻す。戻し忘れると、次のテストの `expect.element` の待ちや MSW の遅延応答が進まない
- MSW は `afterEach` で `resetHandlers()` を呼び、テスト内で上書きしたハンドラを戻す。`onUnhandledRequest: 'error'` にして、ハンドラの漏れを失敗として扱う

### Browser Mode

- `vitest-browser-react` の `render` は、次のテストが始まる前に前のコンポーネントを片付ける（直後ではない）。最後のテストの描画は残る
- 片付けの対象はコンポーネントだけ。同じファイル内のテスト間では、ブラウザの状態が残る前提で書く: localStorage / sessionStorage、cookie、URL と履歴、`document.body` のクラスやスタイル（モーダルの scroll lock など）、viewport のサイズ、フォーカス位置。変えたテストが自分で戻すか、`beforeEach` で初期化する

### モジュールが持つ状態

- モジュールのトップレベルで作って使い回す状態が、一番見落としやすい: 1 つだけ作った QueryClient（キャッシュが次のテストに残る）、zustand などのストア、モジュールレベルのキャッシュやシングルトン
- QueryClient はテストごとに新しく作り、`retry: false` にする。ストアは初期化関数を用意して `beforeEach` で呼ぶ。片付けを書くより、毎回新しく作るほうが確実

### 順序依存の検出

- `sequence.shuffle: true` で実行順をランダムにし、順序に依存しているテストを見つける。CI で定期的に回す

## テスト資産の共通化

- **fixture とハンドラを共通化する**: 同じ fixture・MSW ハンドラを Storybook、コンポーネントテスト、MSW 層の E2E で使い回す。可能なら OpenAPI などのスキーマから型付きで生成する
- **契約は型で守る**: バックエンドとの契約（レスポンスの形）は型やスキーマで担保し、実バックエンド E2E に背負わせない

## レビューの出し方

`test-quality.md` のレビュー手順に加えて、次を確かめる。

1. より安いレイヤーで検証できる観点がないか（「これは単体テストに下げられる」「これは VRT で十分」）
2. 同じ観点を複数のレイヤーで重ねて検証していないか
3. ロジック・API 呼び出し・副作用がコンポーネントに埋まっていて、高いレイヤーでしかテストできない形になっていないか
4. 見た目に影響する変更なのに、対応する Story がない（VRT で守られない）ことがないか
5. ユーザー向け機能なのに、導線のつながりを証明するテストがどこにもないことがないか

指摘には、どのレイヤー（またはどの実装の層）に移すべきかと理由を添える。
