# testable-design

テストしやすさは実装の分け方で決まり、テストの書きにくさは分け方が崩れているサインになる。責務分離とテストの観点を一つの skill で扱うのはそのため。

この SKILL.md には毎回当てる核だけを置く。詳細は `references/` を、必要になったときに読む。

| いまやること | 読むもの |
|---|---|
| アプリケーションコードを書く・直す・レビューする | この SKILL.md、境界に迷ったら `references/separation-of-concerns.md` |
| テストを書く・直す・レビューする | この SKILL.md と `references/test-quality.md` |
| React フロントエンドのテスト（レイヤー選択、Storybook / VRT / MSW、実装の層分け） | 上に加えて `references/frontend-testing.md` |
| JS / TS のプロジェクトで、ツールで先に候補を洗い出す | `references/mechanical-checks.md` |
| 観点の出どころを確かめる | `references/sources.md` |

## プロジェクトの規約との関係

この skill は汎用の既定値。リポジトリにテストの規約（skill、AGENTS.md / CLAUDE.md、レビュー基準）があれば、次はそちらを優先する。

- レイヤーの選び方と既定（例: 操作の検証を Story の `play` に寄せる、全 Story を VRT の対象にする、純粋関数もブラウザで走らせる）
- レビューで扱う範囲（既存テストを指摘するか、指摘の件数や重さ）
- 書き方の具体（import 元、待ち方、片付けを設定で行うか手で書くか、スナップショットの使いどころ）

規約に従うときも、「二つの軸」と「まず書かない判断」は当てる。規約がこの skill と食い違うときは規約に従い、違いを報告に一文で書く。

プロジェクトに無いレイヤー（実バックエンド E2E、MSW の結合テストなど）は、対応表から外して考える。そのレイヤーが無いこと自体は欠落として指摘しない。どのレイヤーでも確かめていない観点が残るなら、その観点を報告に書く。

## 二つの軸

1. **変わる理由が同じものは一か所に集め、違うものは離す**（Martin）。変わる理由は、変更を頼んでくる「人」で数える。行数やファイル数では判定しない。崩れ方は「混ざりすぎ」「散らばりすぎ」「分けすぎ」の三方向にある
2. **一つの振る舞いは、それを確かめられる一番安いレイヤーで、一度だけ確かめる**。実装ではなく、使う側から見える振る舞いを確かめる。リファクタリングへの耐性と保守性は常に最大化する（Khorikov）

二つはつながっている。判定ロジックを確かめるのに DB・API クライアント・現在時刻をまとめてモックしないといけないなら、軸 1 が崩れている。テストを複雑にする前に、必要な値を引数で受け取る純粋関数に切り出す（`isOverdue(deadline, now)`）。

## アプリケーションコードを書くとき

書く前に三つ問う。

1. このコードの変更を頼んでくるのは誰か。二人以上いるなら、どこで分かれるか
2. 「〜を変えたい」という要望を一つ想定したとき、直すのは何か所か。一か所に収まるか
3. いま足そうとしているものは、隣にあるものと同じ理由で変わるか

答えられないなら要件がまだ見えていない。推測で分割や共通化を進めない。

- 共通部にフラグ・`variant`・分岐を一つ足す前に、呼び出し元を分けるほうが自然でないか比べる。見た目が同じコードの重複は、同じ知識の重複とは限らない
- 境界で形を変換する処理を一か所に置き、内側には業務上の値だけを渡す（UI が API レスポンスの奥を辿らない）
- ロジックは純粋関数に、外部とのやり取り（API・時刻・ストレージ）は呼び出し側か専用の層に置く
- 差し替える予定のない層を「将来のため」に挟まない
- テストのためだけに切り出さない。切り出すのは変わる理由が違うときで、テストしやすくなるのはその結果
- 依頼範囲外の既存の崩れは直さず、報告に一文で書く

観点 1〜8 の詳細と症状の見分け方は `references/separation-of-concerns.md`。

## テストを書くとき

### まず書かない判断を当てる

- 期待値を実装と同じ計算で作らない（実装の写し）。仕様・具体例・リテラルから取る
- 内部の協調者へのモック呼び出しを確かめるだけのテストを書かない。呼び出しの検証は外部から観測できる相互作用に限る
- 自明なコード、フレームワーク自体の挙動、型が保証する内容をテストしない
- 同じ振る舞いを単体・統合・E2E で重ねない
- カバレッジ率を目的にしない

既存テストが上に当たるなら、修正ではなく削除を提案してよい。

### 手順

1. **既存の規約を確かめる**: テストの規約を書いた skill や AGENTS.md、テストの設定（Vitest の環境、setup ファイル）、置き場所、命名、ファクトリや MSW ハンドラの有無を調べ、それに合わせる（「プロジェクトの規約との関係」）
2. **観点を列挙する**: 今回の変更で守りたい振る舞いを箇条書きにする（メソッド単位ではなく振る舞い単位）
3. **実装の分け方を確かめる**: 安いレイヤーで確かめられない形なら、切り出しを計画に含める
4. **レイヤーを割り当てる**: 各観点をちょうど一つのレイヤーに割り当てる。フロントエンドは `references/frontend-testing.md` の対応表を使う
5. **重複を確かめる**: 既存のテストや Story が同じ観点を見ていないか探す。あれば足さずに更新する
6. **書く**: given / when / then、テスト名に振る舞いと期待結果、テストにロジックを書かない、時刻と乱数は注入する。詳細は `references/test-quality.md`
7. **走らせる**: 書いたテストを実際に実行する。対象の実装を一時的に壊して落ちることを確かめ、意味のあるテストか確認する。0 件ヒットを pass と扱わない。落ちたら直して再実行し、最後に関連するテストを全件流す

モックが三つ以上要るなら、テストを書き進める前に実装の分け方を見直す。モックは管理外の依存（外部 API、メール送信など）とネットワーク層（MSW）に限る。

## レビューするとき

次の順で当てる。指摘には当たる観点と、壊れる具体シナリオを添える（「管理画面だけ email を出したい要望で `UserCard` に `showEmail` を足すと、生徒画面も一緒に変わる」「`calcTotal` を二関数に分けるとこのテストは落ちるが、振る舞いは変わらない」）。観点名だけの指摘、行数やファイル数だけを根拠にした指摘はしない。

1. 変わる理由の違うものが混ざっていないか、一つの要望の変更が散らばっていないか、共通部にフラグや分岐が増えていないか
2. 書かない判断に当たるテストがないか（あれば削除を提案）
3. テストが実装詳細に結合していないか。具体的なリファクタを一つ想定して判定する
4. より安いレイヤーで確かめられる観点、複数レイヤーで重複している観点がないか
5. ロジックや副作用が埋まっていて、高いレイヤーでしかテストできない実装になっていないか
6. 足りない振る舞い（異常系・境界値）、ユーザー向け機能の導線を証明するテストの欠落がないか
7. 分けすぎていないか、読みやすさ・決定性・速さ

崩れていても今回の変更が新たに悪化させていないなら、既存の問題として分けて書く。

## 機械チェック（JS / TS）

構文から拾える症状と候補は、読む前にツールで洗い出せる。ツールはこの skill のディレクトリの `tools/` にある（実体は `~/.agents/skills/testable-design/tools/`。`~/.claude/skills/` からの symlink でも同じ）。使い方とコマンド例は `references/mechanical-checks.md` にあり、コマンド例は実体の絶対パスで書いてある。

- Oxlint のルール: モックの数と対象、コンポーネントの中の fetch・現在時刻・乱数・ストレージ、`useEffect` の数を報告する
- `testable-scan`: テストから直接 import されていないロジック（テストからモック越しにしか届かないものを区別する）、テストと `play` の両方が import するコンポーネント、モックされているモジュール、story から届かないコンポーネント、層をまたいで同じ期待値を持つテストの組、同じ環境変数を読むファイルのグループを、候補として絞る

ツールは読む範囲を狭めるだけで、判定はしない。報告と候補のファイルを読み、この SKILL.md の観点で判定する。ツールの出力だけを根拠にした指摘はしない。`oxlint` が無いなどで実行できないときは省き、省いたことを報告に一文で書く。
