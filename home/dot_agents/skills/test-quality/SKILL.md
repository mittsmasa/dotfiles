# test-quality

テストを書く前と、書かれたテストをレビューするときに当てる観点。原典ごとの詳細と出典は `references/sources.md` にある。

## 前提: 観点はスライダー

各観点は同時に最大化できない。速さと予測性（本物の依存を使うほど本番に近いが遅い）は特に引っ張り合う。チェックリストとして全部満たそうとせず、そのテストで何を優先したかを説明できる状態にする。

ただし次の 2 つは常に最大化する（Khorikov）。

- **リファクタリングへの耐性**: 実装の構造が変わっただけでは落ちない
- **保守性**: 読めば何を確かめているかわかり、すぐ走らせられる

## 書かない判断

テストを足す前に、まずこの節を当てる。テストの価値は「回帰からの保護 × リファクタ耐性 × 速さ × 保守性」の掛け算で、どれかが 0 に近ければ全体も 0 に近い。

- **実装の写しを書かない**: 期待値を、実装と同じ計算・同じ組み立てで作らない（`expect(add(a, b)).toBe(a + b)` の類）。実装が間違えば期待値も同じだけ間違うので、何も検出できない。期待値は仕様・具体例・リテラルから取る
- **モックの呼び出し順や引数を確かめるだけのテストを書かない**: 内部の協調者とのやりとりは実装詳細なので、リファクタのたびに落ちる。結果の状態や戻り値を確かめる。呼び出しの検証は、外部から観測できる相互作用（外部 API・メール送信・他システムが読むキュー）に限る
- **自明なコードをテストしない**: getter / setter、委譲するだけの関数、型システムが保証する内容。単体テストはドメインロジックとアルゴリズムに集中する。協調者が多いだけでロジックの薄い層（controller、ハンドラ、ページコンポーネント）は、少数の統合テストで覆う
- **1 振る舞いを 1 か所で確かめる**: 同じ振る舞いを単体・統合・E2E で重ねて検証しない。下の層で確かめたことは、上の層では通り道として通過するだけにする
- **フレームワークやライブラリ自体の挙動を確かめない**: 自分のコードが足した振る舞いだけを対象にする
- **カバレッジ率を目的にしない**: 率を上げるために書いたテストは、上の 5 つに引っかかりやすい

既存テストのレビューで上に当たるものを見つけたら、修正ではなく削除を提案してよい。

## 共通の観点

### 何を確かめるか

- **振る舞いを確かめ、実装を確かめない**: 公開 API（関数のシグネチャ、HTTP エンドポイント、画面）経由で、使う側と同じ呼び方をする。private なメソッドや内部状態を覗かない
- **目標は unchanging test**: 一度書いたテストは、要件が変わったときだけ変更が要る。リファクタ・バグ修正・機能追加で直す必要が出たら、実装に結合している
- **メソッド単位でなく振る舞い単位**: 1 メソッド 1 テストにしない。「〜のとき〜になる」1 つにつき 1 テスト
- **異常系を入れる**: 正常系だけでは回帰保護が弱い。境界値、空、エラー応答、タイムアウトを検討する

### どう書くか

- **given / when / then の 3 段**で書き、when と then を交互に混ぜない
- **テスト名に振る舞いと期待結果を書く**。名前に「and」が要るなら 2 つのテストに分ける
- **テストにロジックを書かない**: ループ・条件分岐・凝った文字列組み立ては、テスト自体のバグを生み、読み手が検証できなくなる
- **DRY より DAMP**: 読みやすさのための重複は許す。共通 setup はデフォルトの構築にとどめ、そのテストが依存する値はテスト本文に明示する
- **失敗メッセージで原因がわかる**ようにする（期待値・実際値・関連パラメータ）

### 実行の質

- **Isolated / Deterministic**: 実行順・時刻・乱数・ネットワークで結果が変わらない。時刻と乱数は注入する。テスト間で状態を共有しない
- **Fast**: 遅いテストは走らされなくなる。重い依存は必要な層にだけ持ち込む
- **Hermetic**: 必要な依存はテスト自身が用意する。手元の環境や共有サーバーの状態に依存しない

## フロントエンド固有の観点

- **使われ方に似せる**: ユーザーが見て触るもの（role、ラベル、表示テキスト）で要素を引く。Testing Library のクエリ優先順位は `getByRole` > `getByLabelText` > `getByPlaceholderText` > `getByText` > `getByDisplayValue` > `getByAltText` > `getByTitle` > `getByTestId`。role やラベルで引けないなら、a11y の問題を疑う
- **コンポーネントの内部を見ない**: state、props の受け渡し、hooks の呼び出し回数、CSS クラス名を確かめない
- **ネットワーク層でモックする**: fetch クライアントや hooks を直接モックせず、MSW などで HTTP を差し替える。本番と同じコード経路を通せる
- **コンポーネント全体のスナップショットを避ける**: DOM 構造の変化すべてで落ちるので、振る舞いを確かめていないのに壊れやすい。使うなら小さなシリアライズ結果に限る
- **配分は統合テスト厚め**（Testing Trophy）: 型と lint を土台に、複数コンポーネントをまとめて描画するテストを主力にする。E2E は重要な導線に絞る
- **jsdom の限界を知る**: レイアウト、スクロール、IntersectionObserver などは描画されない。見た目やブラウザ API に依存する振る舞いは実ブラウザ（Playwright、Vitest browser mode）で確かめる
- **VRT は対象を絞る**: デザインシステムと重要画面に限る。動的コンテンツで flaky になりやすい

## バックエンド固有の観点

- **モックは管理外の依存にだけ使う**:
  - 管理下の依存（自アプリだけが読み書きする DB など）はモックせず本物で統合テストする。DB をモックすると、クエリやスキーマの誤りを検出できない
  - 管理外の依存（外部 API、SMTP、他システムと共有するメッセージバス）はテストダブルに置き換え、送った内容を確かめる。外部から観測できる相互作用なので、ここは呼び出しの検証が振る舞いの検証になる
- **本物の依存は使い捨てで立てる**: Testcontainers などでテストごと（またはスイートごと）に立て、状態をトランザクションのロールバックかクリーンアップで戻す
- **外部の失敗を再現する**: 想定外の HTTP ステータス、タイムアウト、遅延応答をテストダブルで起こす
- **サービス境界は契約テスト**（Pact などの consumer-driven contract）で確かめる。後方互換の破壊は契約テストだけでは拾えないので、重要な連携は E2E で補う
- **単体テストはドメインロジックに集中**: controller やハンドラは統合テストで通す

## レビューの出し方

書かれたテストをレビューするときは、次の順で当てる。

1. 「書かない判断」に当たるテストがないか。あれば削除を提案する
2. 実装詳細に結合していないか（リファクタで落ちるか）を、具体的なリファクタ例を 1 つ想定して判定する
3. 足りない振る舞い（異常系・境界値）がないか
4. 読みやすさ・決定性・速さ

指摘には、どの観点に当たるかと、落ちる具体的なシナリオ（「`calcTotal` を 2 関数に分けるとこのテストは落ちるが、振る舞いは変わらない」）を添える。観点名だけの指摘はしない。
