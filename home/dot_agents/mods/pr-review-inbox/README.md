# pr-review-inbox

自分にレビュー依頼が来ている PR を決まった間隔（既定は 1 時間）で集め、読み取り専用の subagent に下読みさせて、結果を pane に並べる mod です。

- 既定では、取得するのは平日 8〜17 時だけです。間隔と時間帯は設定ファイルの `schedule` で変えられます（タイムゾーンは設定メニューの `utcOffsetMinutes`）
- `/review-inbox` で pane を開きます

## 必要なもの

- `gh`（ログイン済み）と `git`
- 下読みする PR のリポジトリの clone（clone が無い PR は「clone なし」と表示されます）

## バンドと通知

下読みが終わったことは、pane を開いていなくても 3 つの形で分かります。出すのは、`/review-inbox` を打った受付中のセッションだけです。

| 形 | 出るとき | 文言の例 |
| --- | --- | --- |
| バンド（入力欄の上） | 自分の番を待つ PR（下読み済み、未送信、片付けていない）が 1 件以上あるあいだ | `PR 待ち 2 · blocker 1 · 開く` |
| toast（画面の右上に 10 秒） | 下読みが終わるたび。5 秒のあいだに終わった分は 1 回にまとめます | `下読み完了 2 件 · blocker 1` |
| OS の通知 | 待機中と下読み中が 0 件になったときに 1 回 | `下読みがすべて終わりました: 5 件 · blocker 1` |

- 件数に入るのは、待機中か下読み中から下読み済みになった PR です。同じ commit の保存済み結果を使い回した PR も入ります。送信済みの結果が戻っただけの PR は入りません
- 再起動や reload では出ません。前から下読み済みだった PR は、バンドにだけ出ます
- 終わってから 5 秒のあいだに片付けた PR は数えません
- OS の通知の件数は、前回の OS の通知のあとに終わった分です。最後の 1 件が失敗で終わったときも、終わった分があれば出します。全部が失敗したときは出ません
- OS の通知は、Claude Code の通知設定（`preferredNotifChannel`）と `Notification` hook を通ります。通知を切っていれば届きません
- toast が出るのは受付中のセッションの画面です。別のセッションを開いているときに見えるかは確かめていません

## 設定ファイル

`~/.config/pr-review-inbox/config.json` に書きます。`sources` か `repos` のどちらも無いと、何も取得しません。

### どのマシンでも要る指示は mod 本体に書く

mod 本体（`~/.agents/mods/pr-review-inbox/`）は chezmoi で全マシンに同期します。一方、`~/.config/pr-review-inbox/` の config.json と guide.md は、マシンごとに下読みの中身を変えるために、あえて同期しません。

このため、guide.md に足した指示は、そのマシンでしか効きません。

- 観点に依らない reviewer への指示（機械チェックの出力を必ず読む、など）は、mod の prompt（`hooks/reviews.ts`）に書きます。guide.md に書くと、ほかのマシンの下読みでは抜けます。結果の形は変わらないので、抜けに気づきにくいです
- guide.md には、そのマシンで当てる skill の読み方だけを書きます

### team で使う最小の例

org 内の依頼をすべて拾い、clone は `~/work/repo/<リポジトリ名>` にある前提です。

```json
{
  "sources": ["your-org"],
  "clonePath": "~/work/repo/{repo}"
}
```

### キー

| キー | 意味 | 書かなかったとき |
|---|---|---|
| `sources` | 検索対象の配列。`owner` なら org 全体、`owner/repo` ならそのリポジトリ | `repos` のキー |
| `clonePath` | clone の場所。`{owner}` と `{repo}` を差し込みます。`{repo}` は必須です | `repos` に無いリポジトリは「clone なし」 |
| `repos` | `owner/repo` ごとの clone の場所。`clonePath` より優先します | なし |
| `criteria` | リポジトリごとのレビュー基準ファイル（clone 内のパス）と、対象にする変更パスの正規表現 | なし |
| `review` | 下読みの中身（次の節） | 観点ファイルなし、機械チェックなし |
| `schedule` | 自動取得の間隔、曜日、時間帯（「schedule」の節） | 1 時間ごと、平日 8〜17 時 |

`criteria` の例です。

```json
"criteria": {
  "your-org/your-repo": { "path": "docs/review-criteria.md", "applies": "^frontend/" }
}
```

### review: 下読みの中身を差し替える

| キー | 意味 | 書かなかったとき |
|---|---|---|
| `viewpoints` | reviewer に読ませる観点ファイルの配列（読む順）。ファイルのパスか glob で書きます。ディレクトリをそのまま書くと無視されます | なし。差分と `criteria` だけで下読みします |
| `guide` | 観点ファイルの使い方と、観点由来の指摘の書き方を書いたファイル。中身が prompt に入ります。観点由来の指摘の `source` は `"viewpoint"` です | 汎用の短い指示 |
| `commentStyle` | コメント下書きの口調を書いたファイル。中身が prompt に入ります | です・ます調で、問題、理由、直し方の案を 1〜3 文で書く |
| `checks` | 機械チェックの配列 | なし。機械チェックをしません |

`viewpoints` は glob でも書けます。skill の `references/` までまとめて読ませたいときに使います。

```json
"viewpoints": [
  "~/.agents/skills/testable-design/SKILL.md",
  "~/.agents/skills/testable-design/references/*.md",
  "~/.claude/skills/team-review/**/*.md"
]
```

- `*` と `?` は 1 階層の中だけに合います。`**` は 0 階層以上のディレクトリに合います。`{a,b}` は a か b に合います
- glob に合ったファイルはパス順に並べます。配列の順はそのまま保ちます。同じファイルが 2 回出たら、最初の位置だけに残します
- `.` で始まる名前は、ファイルもディレクトリも拾いません。シンボリックリンクは辿ります
- 1 つの glob で拾うのは 100 ファイル、辿るのは 8 階層・500 ディレクトリまでです。超えたときと、何にも合わなかったときは、設定の誤りとして pane に出ます
- `tools/` のスクリプトを拾わないように、`*.md` などで拡張子を絞ってください。reviewer が読めるのは、展開して拾ったファイルだけです
- 設定ファイルと同じく、展開はセッションの開始時と `/review-inbox` のときに 1 回だけです。あとから skill にファイルを足したら `/review-inbox` を打ち直します

`checks` の各項目は次の形です。

```json
{ "name": "oxlint", "argv": ["oxlint", "-c", "~/lint/oxlintrc.json", "-f", "json", "{files}"], "stdout": "oxlint.json" }
```

- `argv` は shell を通さずに実行します。`argv[0]` は絶対パスか、PATH 上のコマンド名です
- 置き換わる値:
  - `{files}`: 変更された JS / TS ファイルの絶対パス（1 ファイル 1 引数）
  - `{relativeFiles}`: 同じファイルの worktree からの相対パス。`./` から始まります
  - `{worktree}`: PR の checkout
  - `{outDir}`: 出力先のディレクトリ
- 変更に JS / TS ファイルが無い PR（workflow や Dockerfile だけの変更など）では、`{files}` か `{relativeFiles}` を持つチェックだけを省きます。pane の「省いたもの」に「<name>（対象の JS / TS ファイルなし）」と出ます
- どちらも持たないチェックは、変更の中身にかかわらず毎回走ります。`{worktree}` を渡して checkout 全体を走査するチェックはこちらです

```json
{ "name": "secure-scan", "argv": ["~/.local/share/mise/shims/node", "~/.agents/skills/secure-dev/tools/bin/secure-scan.ts", "{worktree}", "--out", "{outDir}"], "outputs": ["findings.json"] }
```

- `stdout` を書くと、標準出力を `{outDir}/<stdout>` に保存します
- `outputs` には、コマンドが自分で `{outDir}` に書くファイル名を並べます。終わったときにこれが無ければ、そのチェックは失敗扱いです
- 終了コードは見ません。lint は指摘があると 0 以外で終わるためです。起動できない、タイムアウト（3 分）、`outputs` が無い、のどれかで失敗になり、pane に「省いたもの」として出ます

設定の誤り（読めない項目）は既定値に倒し、取得のあとに pane へ「取得に失敗しました: 設定の誤り: …」と出ます。取得そのものは成功しています。

### schedule: 自動取得の間隔と時間帯

書かなければ、1 時間ごと、平日 8〜17 時に取得します。書いたキーだけが変わります。

```json
"schedule": { "intervalMinutes": 30, "days": [1, 3, 5], "fromHour": 9, "toHour": 19 }
```

| キー | 意味 | 書かなかったとき |
|---|---|---|
| `intervalMinutes` | 自動取得の間隔（分）。5〜1440 の整数 | 60 |
| `days` | 取得する曜日の配列。0 が日曜、6 が土曜 | `[1, 2, 3, 4, 5]`（平日） |
| `fromHour` / `toHour` | 取得する時間帯。`fromHour` 時から `toHour` 時の手前までです。0〜24 の整数で、`fromHour` を `toHour` より小さくします | 8 / 17 |

- 下限の 5 分は、GitHub に問い合わせすぎないためです。取得のたびに、検索と PR ごとの `gh pr view` が走ります
- 日をまたぐ時間帯（22 時〜翌 6 時など）は書けません
- 読めない値は、そのキーだけ既定値に戻し、設定の誤りとして pane に出ます。`fromHour` と `toHour` は 2 つ組で既定値に戻ります
- 時間外は、pane の見出しに「時間外 · 月水金 9–19 時だけ自動取得」のように出ます
- ほかのキーと同じく、読み直すのはセッションの開始時と `/review-inbox` のときです。書き換えたら `/review-inbox` を打ち直します

## 詳細ビュー

PR を選ぶと、上から順に次が並びます。

1. タイトルと、`深掘りする`、`差分を見る`、`片付ける`、`GitHub で開く`
2. 概要（PR の本文）。4 行以上なら 3 行に畳み、`続きを表示` と `折りたたむ` で開閉します
3. 指摘
4. 省いたもの。下読みが確認できなかった事柄があるときだけ、1 行で出ます
5. PR コメント欄と送信ボタン

PR コメント欄は、承認できる PR にだけ出ます。初期値は `LGTM!` です。`承認して送る` を押すと、欄の文面を本文にした確認が出ます。欄を空にすると、本文なしで承認します。

## 再レビュー

以前に自分がレビューした PR には、一覧の行に `再レビュー` が付きます。詳細ビューには、前回のレビューの日付と状態（`再レビュー · 前回 11/16 コメント`）が出ます。GitHub に聞くので、この mod を通さずに出したレビューも数えます。

前回、自分が始めたスレッドは「前回の指摘」として、概要と指摘のあいだに並びます。1 件ごとに次が出ます。

- GitHub の事実: `解決済み`、`行が変わった`（指摘した行のコードが変わった）、`返信 n`
- 下読みの判定: `下読み: 対応済み`、`下読み: 未対応`、`下読み: 判断できない` と、その理由。下読みが今のコードを読んだ見立てなので、外れることがあります
- 自分のコメントと、最後の返信（どちらも途中まで）

注意すること:

- 下読みの判定は、下読みのときに前回の指摘があった PR にだけ付きます。付いていない PR は `もう一度レビューする` を押すと付きます
- レビューの本文に書いた指摘は拾いません。行に付けたコメント（スレッド）だけが対象です
- スレッドは 30 件まで、返信は新しい 3 件まで持ちます
- 取得のたびに、PR ごとに GitHub への問い合わせが 1 回増えます。読めなかった PR は、前に読めた内容のままになります
- 返信はほかの人が書いた文です。画面には文字としてだけ出し、下読みには「データ」として渡します

### 新しい commit が来たとき: 差分の下読み

PR に新しい commit が来ると、下読みは PR 全体を読み直さず、前に下読みした commit からの差分を読みます（差分の下読み）。実測では、前回からの差分は base との diff の約 5 分の 1 でした（1 件の PR での値です）。

reviewer に渡すものは、全体の下読みで渡すものに次の 2 つを足したものです。

- 前に下読みした commit から今の head までの差分（`git diff <前の commit> HEAD`）
- そのときの下読みの指摘と「人間が見るべき観点」

reviewer は次のように読みます。

- 前回からの差分は全部読みます。差分が触れた関数は、呼び出し元と呼び出し先を checkout で確かめます
- base との diff も渡します。PR 全体の形を見るためで、変わっていない部分は判定し直しません
- 前の指摘は、今のコードで 1 件ずつ確かめます。まだ当てはまる指摘は、今の行番号で指摘に載せ直します。直っていた指摘は載りません

差分の下読みをした PR には、詳細ビューの「省いたもの」に `前回（2931cf0）から変わっていない部分の読み直し` と出ます。括弧の中は、前に下読みした commit です。

「前に下読みした commit」は、その PR の受理済みの結果（`results/<owner>/<repo>/<PR 番号>/<sha>.accepted.json`）のうち、今の head 以外で一番新しいものです。ディスクから探すので、レビューを送って一覧から消えた PR に再依頼が来たときも使えます。

次のときは、PR 全体を読み直します。

- 前の commit の受理済みの結果が無い、または読めない
- 前の commit が今の head の祖先でない（force-push、rebase）。前の commit が clone に無いときも含みます
- 差分の下読みが 3 回続いた。4 回目は全体を読み、数え直します
- `もう一度レビューする` を押した
- レビューを送ったあと、同じ commit のままでもう一度依頼された
- 前回からの差分が 3,000,000 字を超える

「前回の指摘」（GitHub のスレッド）との違い:

| | 前回の指摘 | 差分の下読みが持ち越す指摘 |
|---|---|---|
| 中身 | GitHub に送ったコメントと、その返信 | mod が前の commit の下読みで出した指摘。送っていないものも含みます |
| 下読みの出し方 | `下読み: 対応済み / 未対応 / 判断できない` | まだ当てはまるものを、指摘として載せ直す |

同じ指摘が両方にあるときは、「前回の指摘」の側だけに出すよう reviewer に頼んでいます。

注意すること:

- 差分の外に影響が出る変更（差分に無い呼び出し元が壊れる、など）は、全体の下読みより見落としやすくなります。気になる PR は `もう一度レビューする` で全体を読み直せます
- 前の下読みで外した指摘も、今のコードに当てはまれば、また載ります。外したかどうかはディスクに残していないためです。全体の下読みでも同じ指摘が出るので、今までと変わりません
- 作者が base を merge で取り込むと、前回からの差分に base 側の変更が混ざります。reviewer には「base との diff に無い変更は読み飛ばす」と頼んでいますが、読む量は増えます
- `もう一度レビューする` を押してから下読みが始まるまでに mod が読み直されると、全体ではなく差分の下読みになることがあります。「省いたもの」に出るので、もう一度押してください
- 機械的なチェック（`checks`）は、今までどおり PR の変更ファイル全部に走ります

## 差分ビュー

`差分を見る` を押すと、pane がその PR の差分の画面に替わります。diff が保存されている PR にだけ出ます。`← 詳細` で戻ります。

- ファイルの一覧が、追加と削除の行数、指摘の数つきで並びます。ファイル名を押すと、その下に差分が開きます。開くのは 1 つだけです
- 下読みの指摘と自分のコメントは、その行の真下に出ます。行が差分に無い指摘は、ファイルの先頭に「このページに無い指摘」として出ます
- 行番号を押すと、その行へのコメントを書けます。足したコメントは詳細ビューの指摘にも並び、ほかの指摘と一緒に送られます
- 削除行にもコメントを書けます。GitHub には、変更前の行（`side: LEFT`）として送ります。詳細ビューでは `削除行` のタグが付きます。レビューの API がこの指定を受けることは、GitHub の文書からの推測です。最初に送るときは、GitHub で赤い行に付いたかを見てください
- 既定では、空白だけの変更を隠します。字下げだけが変わった行は、変更なしの行として出ます。`空白の変更も表示` で保存した diff のまま出し、`空白の変更を隠す` で戻します。隠す処理は mod の中で行うので、`git diff -w` や GitHub の Hide whitespace と結果が違うことがあります
- 指摘の編集と「外す／戻す」は詳細ビューでします。足したコメントを取り消すときも、詳細で「外す」を押します
- 送信済みの PR と、送信の確認中は、差分を読めますが、コメントは足せません
- 長いファイルは 100 行ずつ出ます。`前へ` と `次へ` で行き来します。デスクトップアプリが、行の多い木を描かないためです。ほかのページの行に付いた指摘は、行番号（`L508`）を添えてファイルの先頭に出ます。`この行へ` を押すと、その行のページに移ります
- 1 つのファイルで持つのは 50,000 字か 1,000 行までです。超えた分は `GitHub で続きを見る` から読みます
- 言語の色付けはありません。追加と削除の色だけが付きます

## 深掘りと worktree

`深掘りする` は、別セッションでのレビューを頼む依頼文を作ります。入力欄に入れられないとき（デスクトップアプリ）はクリップボードにコピーするので、貼って送ります。

依頼文には次の 2 つが入ります。

- 下読みが使った worktree の場所（`<clone>/.claude/worktrees/review-<PR 番号>`）
- 下読みの結果の場所（`~/.cache/pr-review-inbox/results/<owner>/<repo>/<PR 番号>/<sha>.accepted.json`）

worktree は PR の head そのものです。中身は信頼しないでください。次の PR では、worktree の場所を依頼文に入れず、結果の場所だけを入れます。その worktree でセッションを開くと、PR が足した設定や指示が読み込まれうるためです。

- どこかの階層の `.claude/` 配下、`CLAUDE.md`、`CLAUDE.local.md`、`AGENTS.md`、`.mcp.json` を変えている PR
- 変更ファイルの一覧を全部は取得できなかった PR

worktree は下読みが終わっても残り、次のどれかで消えます。深掘りのセッションが開いていても消えます。

- `片付ける` を押す
- レビューを送る
- `もう一度レビューする` を押す、または PR に新しい commit が来て下読みし直す
- PR が一覧から消える（マージ、依頼の取り下げ）。次に取得が成功したときに消えます

一覧から消えた PR の worktree は、取得のたびに `<clone>/.claude/worktrees/` を見て探します。名前が `review-<数字>` で、その番号の PR が一覧に無く、下読み中でも準備中でもないものを消します。以前から残っていた worktree も同じ条件で消えます。

- `review-<数字>` はこの mod が使う名前です。同じ場所に同じ形の名前で自分の worktree を作ると、未コミットの変更ごと消えます
- 消えるのは worktree だけです。`~/.cache/pr-review-inbox/` の保存済みの結果、diff、機械チェックの出力は残ります。同じ PR がまた依頼されたときに使えます
- 取得に失敗したときと、検索が 1 つの `sources` で 50 件（上限）を返したときは、何も消しません。一覧に無い PR が、本当に消えたのか、取れなかっただけなのかを区別できないためです
- 見に行く clone は、`repos` に書いたもの、`sources` に `owner/repo` で書いたもの、一覧に載った PR のものです。`sources` に `owner` だけを書き、`clonePath` で場所を決めている clone は、その PR が一覧に載った取得のときだけ見ます

保存済みの結果を使い回した PR には worktree がありません。

## セルフレビュー

自分の PR を作る前に、同じ下読みで自分のブランチを読みます。観点、guide、機械チェック、reviewer への依頼文、結果の受理条件は、レビュー依頼の下読みと同じです。pane には出ません。

PreToolUse hook に次を足すと、Claude Code のセッションが `gh pr create` を打ったときに止めて、下読みの手順を返します。

```json
{
  "type": "command",
  "command": "~/.local/share/mise/installs/node/global/bin/node ~/.agents/mods/pr-review-inbox/tools/self-review.ts gate",
  "if": "Bash(gh pr create *)"
}
```

- node は 22.18 以降が要ります。`.ts` をそのまま走らせ、mod の拡張子なしの import を `registerHooks` で解決するためです
- 止めるのは、origin が `sources` に入っているリポジトリの `gh pr create` だけです。`&&` や `|` でつないだ呼び出しと、`--dry-run` は止めません
- 手順は 3 つです。`prepare` が diff、機械チェックの出力、依頼文を書きます。セッションが依頼文を general-purpose の subagent に渡します。`report` が結果を受理して、修正リストを出します
- ブランチのどこかの commit（`origin/<base>` に入っていないもの）に受理済みの結果があれば通します。指摘を直して commit しても、もう一度下読みは求めません
- 結果は checkout の `.workflow/self-review/<sha>/` に置きます。`.workflow` を gitignore していないリポジトリでは、未追跡のファイルとして見えます
- ユーザーが指示したときだけ、`self-review.ts skip --reason "<理由>"` で下読みを飛ばせます

レビュー依頼の下読みとの違い:

- 読むのは作業ツリーそのものです。worktree は作りません。diff は `origin/<base>...HEAD` で、fetch はしません。未コミットの変更は diff に入らず、「省いたもの」に出ます
- PR の会話と checks、前回の指摘は渡しません（PR がまだ無いため）
- reviewer のツールを絞りません。読む対象が自分のコードだからです
- `/review-inbox` を打った受付セッションでは、mod のガードが subagent を止めるので下読みできません。別のセッションで下読みするか、skip します

## reviewer が触れるもの

reviewer は Read / Grep / Glob と、結果ファイル 1 つへの Write だけを使えます。読めるのは次の範囲に限られます。

- PR の checkout
- diff と機械チェックの出力
- `criteria` のファイル（clone 内にある場合だけ）
- `viewpoints` のファイル（glob は展開したあとのファイル）
- PR の会話と checks（下読みを始めるときに mod が `gh pr view` で取り、機械チェックの出力と同じフォルダに `conversation.json` として置きます）

reviewer 自身は gh を使えません。PR のコメント、レビュー本文、checks の結果は、mod が取ったものだけを読みます。取得に失敗したときは下読みを続け、結果の `skipped` に「PR の会話と checks（取得失敗）」と残します。

コメントとレビューは新しい順に 30 件まで、本文は 1 件 2000 字までです。bot が同じコメントを上書きし続ける場合（VRT の結果や Storybook のプレビューなど）、そのコメントの日時は最初に投稿したときのままです。コメントが 30 件を超える PR では、こうしたコメントが先に落ちることがあります。
